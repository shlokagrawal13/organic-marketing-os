# Workspace settings revision guard (UX-01F)

Two authorized editors can open the same name/timezone settings. Before this increment, a later manual save silently replaced the earlier one. Existing workspaces receive `settingsRevision = 0` through a defaulted, non-null column in migration 25; no prior migration is changed. A successful settings PATCH requires the integer `expectedRevision` read with the settings, atomically matches that revision for the tenant organization, increments it once, and writes one tenant audit record with the new revision. A stale or missing revision cannot write or create an audit record. Reading remains governed by the existing tenant membership guard; only OWNER and ADMIN may write.

The settings editor sends its last acknowledged revision with the explicit Save workspace action. A 409 conflict keeps the local name/timezone and blocks another save until a user confirms reload. Export includes the exact draft, last acknowledged values and revision, and a conflict flag. Cancelling reload preserves the proposal. An acknowledged reload replaces the proposal with the latest server values; the user can review/merge manually before saving. The existing timeout/lost-response path remains separate: it treats the write as uncertain, never retries automatically, and also requires a confirmed reload. Validation and permission errors retain drafts without claiming a conflict or a committed save.

The API's revision applies to workspace name/timezone writes through this endpoint. It does not offer field-level merge, settings autosave, browser-crash durability, or automatic conflict resolution. Other editors, nested workspace UX, production load/accessibility and live/deployed/full-master acceptance remain open. The 24 Compose recovery phases and all earlier recovery assertions remain in place; recovery fixture work is closed at P. CI verifies isolated fixtures, not a deployment.
