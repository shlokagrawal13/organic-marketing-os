# Private-object restore failure and clean retry

RECOVERY-01D adds one phase to the existing disposable Compose verifier (fourteen total). It changes verification harnesses only; application code, dependencies, migration SQL and all three CI jobs remain unchanged. Run `MOS_ALLOW_NATIVE_TESTS=isolated-test-services npm run verify:compose`; `--config-only` establishes configuration isolation, not native restore acceptance.

After the native atomic database restore, the fixture restores private objects sequentially. A controlled exception occurs **after the first actual S3 PUT has returned successfully**. The one-off process exits nonzero. This is an acknowledged-write boundary experiment, not an S3 server/network fault or an actual killed process.

The host requires that exact failure, rejects an application-start callback, and inspects actual Compose state: API, web and all three worker services must be absent. Another one-off inspector lists and reads the real MinIO objects; exactly the first saved object must remain with matching bytes/hash, content type, cache control and metadata. Native recovery job, account, reservation and ledger rows must still match their saved baseline.

Before deleting anything, the host rereads and validates the complete saved database/object manifest, requires the matching generated restore project, validates its Compose configuration and actual media-volume ownership label, and checks application services again. The cleanup helper reads and validates the entire residual set against the expected first object before its first deletion. Unexpected keys, bytes or metadata abort cleanup. It deletes only those exact keys from that restore bucket and verifies the bucket is empty. It does not reset PostgreSQL or Redis, remove source/user storage or use broad pruning.

The same saved backup is then validated and retried. Every object is read back and matched by hash and metadata, and the native recovery rows must remain unchanged. The application-start gate records success only after complete object verification, database baseline checks and a second unchanged-manifest check. It rereads and validates the manifest again before invoking actual API/web/migration startup. Failed or incomplete attempts cannot open the gate.
