RECOVERY-01J extends the disposable Compose verifier with an eighteenth phase. All previous seventeen phases, native corrupt-base/missing-WAL/unreachable-target controls, logical restore, object failure/retry, tenant/revision/credit and worker restart assertions remain. The standalone physical CLI retains its original 19-row fixture. J uses the same 24 unchanged migrations and 37 application tables, with UUID organization/resource IDs, synthetic pre-target password hashes, frozen queued-job context and an additional CLIENT user/membership: 21 rows in 11 tables. No application, migration, dependency or CI workflow changes are required.

The native source and recovery container still has no network, published port or persistent volume. Before PostgreSQL creates its named target, J captures the exact application snapshot and the sole Asset's real version ID/bytes/metadata in a separate owned MinIO bucket. Later SQL removes the Asset and changes approved content; later S3 writes overwrite/delete the current object. A synthetic provider accepts a post-target external operation for the recovered RUNNING AI job. Its request hash binds the recovered job ID, request key, task and input; its confirmed operation ID and reviewed DO_NOT_REPLAY receipt bind the exact native target LSN. This is a deliberately enumerated harness inventory, not proof of real-provider completeness or a production review workflow.

After the native recovery independently matches the target, the harness cleanly stops that recovered cluster and streams its physical data directory in memory. It restarts the native cluster so all original restored-write/constraint/source-preservation checks still run. A separate generated Compose project imports the physical bytes into a newly created empty owned volume. The receiver hashes the actual transferred archive before extraction; the complete application rows and column metadata must independently match the recovered target before any application writer starts. This is a physical cluster copy, with no logical SQL dump or host backup file. Only the copied cluster's listen/socket/archive settings are adapted for its isolated internal network. PostgreSQL has no published port; fixture trust authentication is confined to this disposable network. The real .env and populated user services/volumes are never used.

The exact retained historical version is read explicitly and restored under the original application key in the new private application bucket. Before startup, the verifier re-reads the imported database, actual bucket bytes and Redis key count, checks that all five writers are absent, and compares the complete queue inventory with the pinned recovered snapshot. Missing objects, current Redis keys, altered queue inventory, unreviewed reconstruction, missing receipts, replay dispositions and unreviewed receipts all deny callbacks. Unit controls additionally reject altered physical transfer/snapshot, wrong bytes/extra objects, unknown/wrong-point effects and unsupported render/media/publication inventories. This bounded fixture permits only its enumerated AI jobs; other job families fail closed rather than inheriting an implied review.

Successful admission starts the actual NestJS API, Next.js web and all three workers without running migrations over the copied schema. Restored users sign in through the real authentication API. The owner reads the historical three-byte Asset and a range; anonymous/cross-tenant access and CLIENT writes are denied. Owner editing invalidates approval and advances revision, while a stale edit conflicts. Fresh Redis reconstructs one queued AI job against the synthetic provider. The post-target uncertain operation is not replayed; its recovered RUNNING job fails for review. Exactly one credit consumption is allowed, original ledger entries remain immutable, and all three workers must complete new dispatcher cycles after restart without changing terminal rows, provider counts or credits. The original application's six objects and saved database baseline must remain unchanged. Owned buckets, generated projects and volumes are cleaned up.

Scope remains bounded. The Asset bytes are the original synthetic `old` payload with an image MIME label, not a decoded/renderable image quality test. J exercises one queued AI job, one uncertain external effect and idle render/media dispatcher restart; it does not execute populated render/media/publication jobs against the physical copy. Existing logical recovery phases still execute their separate render/private-output paths. No real provider, live publication, payment or deployment is performed. Production backup scheduling, durable/remote archives, encryption, access policies, retention, operational RPO/RTO, live/deployed and full-master acceptance remain open. CI verifies fixtures and does not deploy. Portable source ZIPs are not database/media backups.

Local verification retained three failed attempts and their successful fixture cleanup. First, host-port readiness could not reach the internal-network fixture; J now publishes no ports and probes actual API/web/proxy readiness inside that network. Second, parsing a SQL timestamp without timezone in the Windows host timezone shifted the expected immutable-ledger dates by 5:30. The comparison now explicitly interprets the fixture's stored UTC timestamp before matching Prisma's ISO representation, with a regression across UTC, Asia/Kolkata and America/Los_Angeles. Third, all J application/worker checks passed but the original native replay telemetry was NULL after the clean export restart. The exact `pg_last_wal_replay_lsn()` target assertion now runs before that optional export; after the hook, `pg_current_wal_lsn()` must additionally remain beyond the target. Every ledger field/timestamp and original native replay assertion remains; no failure is counted as a pass.
