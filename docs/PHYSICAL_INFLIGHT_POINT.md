# Online physical point with live worker claims

RECOVERY-01N extends the isolated Compose recovery fixture with a twenty-second phase. The first twenty-one phases and their assertions remain. The source is the already verified physical application restore with 30 synthetic rows across the complete 37-table, 24-migration schema. It runs the actual compiled render and media workers until both acknowledge their private-object barriers; the fixture provider has accepted one additional request but its response is withheld. The three database claims are live at this point.

The fixture pauses only its two owned worker containers to freeze their heartbeat writes while taking an online `pg_basebackup`. PostgreSQL's `pg_verifybackup` checks the native backup manifest. A SHA-256 of that manifest and the exact tar bytes, the complete application row/column snapshot, all four private objects and their exact bytes, the three claim run-token hashes, and the synthetic provider acceptance receipt form a pinned review. Source rows are compared again after the backup; a changing source rejects the capture. The first local attempt caught exactly such a heartbeat change before the pause guard was added. Both owned workers are then unpaused in `finally`, and the existing SIGKILL/lease-expiry/Redis reconstruction assertions continue.

The tar is imported into a second generated, labeled, empty PostgreSQL volume. Its complete restored snapshot must equal the captured source snapshot. Exact private objects are restored into the new fixture store. No API or worker container may exist there, and fresh Redis must contain zero keys. Admission demands the pinned review and identical backup, rows, object bytes, claim tokens and provider receipt. Nine changed-row/object/review/provider/backup/Redis/writer controls reject before the sole valid callback. The accepted provider request remains `UNKNOWN_REVIEW_DO_NOT_REPLAY`; no second submission is authorized. The predecessor M phase independently checks the actual worker kills, natural lease expiry, explicit owner render retry, exact credit settlements and restart stability.

This is a **second online physical point**, captured after workers claim work in the restored fixture. It does not show those claims or provider acceptance at the earlier named WAL target. The provider is a synthetic internal fixture, not a live billing or inventory authority. S3 and PostgreSQL captures are verified against a stable paused fixture; this does not establish an atomic production cross-store PITR protocol. Redis is intentionally rebuilt empty. Production backup scheduling, remote retention/durability, encryption/access controls, measured RPO/RTO, live-provider reconciliation, populated publication, deployment and full-master acceptance remain open. No populated user service, real `.env`, media volume or private backup is used as a fixture. The source ZIP is portable source/context, not a native backup.
