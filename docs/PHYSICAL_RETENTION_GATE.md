# Retained WAL target and private-object recovery set

RECOVERY-01O adds a bounded recovery-set admission check to the disposable Compose verifier. The existing named PostgreSQL target contains the populated application schema and queued work. The native fixture copies its verified base backup and WAL archive to separate paths, verifies the copied backup with `pg_verifybackup`, checks the target WAL segment digest, and performs the successful named-target promotion from those retained copies. Missing and changed target-segment controls must deny the recovery-start callback. Earlier corrupt-base, missing-WAL, unreachable-target, target-row, timeline and source-preservation assertions remain.

At the populated process-interruption recovery, the pre-target S3 manifest, restored 37-table application snapshot, named target receipt, retained base/WAL identity and reviewed provider-effect receipts form one pinned recovery review. Immediately before application writers start, the gate rereads the retained physical files and exact historical S3 version bytes, then checks every private object restored to the isolated application bucket. Redis must be empty and writers absent. Nine changed-evidence controls deny the callback; the valid set runs the existing tenant/role/queue/credit/media startup checks. The prior online point with actual in-flight claims remains a separate phase with its own physical backup and replay-denial review.

The fixture copies are on one generated tmpfs container and the historical versions live in one generated MinIO stack. They are removed after verification. This proves exact recovery-set preflight and use of a retained local copy, **not** independent-site durability, storage immutability, archive scheduling or atomic PostgreSQL/S3 PITR. The named target precedes actual worker claims; the later in-flight point is an online backup rather than WAL replay to that target. Synthetic provider receipts do not reconcile a real provider. CI verifies fixtures and does not deploy.

Before production recovery can be accepted, operators need a protected base backup plus a continuous WAL archive covering the desired target, retained historical private-object versions with an exact reference manifest, independently protected copies, encryption/access and expiry policy, periodic restore drills, measured RPO/RTO, secret/config recovery, provider-effect reconciliation and a reviewed traffic-switch procedure. Redis must be reconstructed only after the database/object point and external effects are approved. The source ZIP contains none of those native backup bytes. See `docs/qa/recovery01o-evidence.json` for the bounded checks and results.
