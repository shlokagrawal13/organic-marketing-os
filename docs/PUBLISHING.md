## SOCIAL-01 YouTube account connection (local, unpublished) — 2026-10-09 UTC

An authenticated workspace OWNER or ADMIN can start a YouTube connection with `POST /api/workspaces/:organizationId/social-connections/youtube/authorize`. The response contains a Google consent URL with offline access, S256 PKCE and a random state. Redis holds the verifier and user/workspace/session binding for up to ten minutes. `GET /api/social/youtube/callback` consumes that state atomically, checks the same signed-in session and current owner/admin role, exchanges the grant, accepts exactly one owned channel and stores tenant/account-bound encrypted access and refresh tokens. Reauthorization updates the same channel record. The callback redirects to the web origin with only `youtube=connected` or `youtube=failed`; it does not expose the code, state or tokens. The safe connection list returns metadata only. An expired session returns 401 before state consumption.

Configure server-only `YOUTUBE_OAUTH_CLIENT_ID`, `YOUTUBE_OAUTH_CLIENT_SECRET`, the exact registered HTTPS `YOUTUBE_OAUTH_REDIRECT_URI` ending `/api/social/youtube/callback`, and `SOCIAL_TOKEN_ENCRYPTION_KEY` before use. The callback depends on the existing signed-in browser cookie and an available Redis/database. There is no account-connect UI yet. Existing `:id/revoke` marks the local record revoked and gates internal attempts; Google grant revocation, refresh rotation, verified provider lookup, dispatch, scheduler and authorized live posts remain future work. Isolated provider fixtures exercise the API; no Google account was connected or post sent. This source is local and has no own public native CI yet. Earlier sections are dated history.
