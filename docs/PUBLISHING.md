# Publishing status

The current content states are DRAFT → REVIEW → APPROVED, plus ARCHIVED. Editing invalidates approval. An optional `plannedAt` records editorial intent only and does not enqueue a publication. Calendar copy makes that limitation explicit. Content can be exported as JSON for manual use.

The local SOCIAL-01 foundation exposes tenant-scoped `GET/POST /api/workspaces/:organizationId/publication-intents` and `GET /:id`, `POST /:id/cancel`. An approver can prepare an immutable snapshot of a currently approved content revision using a UUID request key. A Video also requires a successful, approved render for that exact revision; non-video preparation rejects a render. The platform is copied from the approved content. A matching request key returns the existing preparation (including its canceled/invalidated state), and a reused key with different input conflicts. Content edit, approval removal or archive invalidates active preparations; historical snapshots remain for audit. Preparation returns `externallySubmitted: false` and never enqueues a post. A cancel is permitted for workspace writers while still prepared. A tenant outsider cannot access the record.

The current local SOCIAL-01 increment adds an internal YouTube connection schema with AES-256-GCM encrypted token fields (tenant/account-bound associated data), safe metadata listing, and owner/admin revocation. The future OAuth callback is not wired; no real account or token can be created through the API. Revocation blocks reserved attempts and marks in-flight submissions UNKNOWN, but does not itself revoke a token at Google. A separate internal ledger reserves one attempt per preparation, requires an unrevoked/unexpired connection with the upload scope and the same approved render/revision, commits SUBMITTING before any possible outbound call, and records a definite receipt/rejection or UNKNOWN. A stale SUBMITTING attempt becomes UNKNOWN without a retry. An uncertain attempt may be confirmed only through a future verified read-only provider lookup; this internal function currently trusts its caller and has no live lookup implementation. Another attempt on the same account/content revision is blocked while the prior state is unresolved or confirmed. No HTTP submit route, automatic scheduler, publication worker, provider request or real post is wired. No UI should label a planned item or preparation as scheduled or published. No preparation is a policy clearance or consent to post.

The next phase must use an official OAuth app and authorized account. Complete token rotation/revocation with the provider, per-platform policy and metadata validation immediately before send, and an authenticated worker/adapter that checks authorization again before token use. Receipt authenticity and read-only lookup results must be verified before calling the internal outcome function. Add scheduler/queue controls and a separately authorized test post. A timeout must never trigger a blind duplicate post.

The AE + SOCIAL-01 foundation was published at `78b78a9` and its own native CI passed (188 unit, 8 HTTP, 7 browser, 5 recovery; 13 migrations). This verifies internal preparation behavior, not an external post. See `docs/qa/editor01ae-social01-native-ci-evidence.json`.
