# Publishing status

The current content states are DRAFT → REVIEW → APPROVED, plus ARCHIVED. Editing invalidates approval. An optional `plannedAt` records editorial intent only and does not enqueue a publication. Calendar copy makes that limitation explicit. Content can be exported as JSON for manual use.

The local SOCIAL-01 foundation exposes tenant-scoped `GET/POST /api/workspaces/:organizationId/publication-intents` and `GET /:id`, `POST /:id/cancel`. An approver can prepare an immutable snapshot of a currently approved content revision using a UUID request key. A Video also requires a successful, approved render for that exact revision; non-video preparation rejects a render. The platform is copied from the approved content. A matching request key returns the existing preparation (including its canceled/invalidated state), and a reused key with different input conflicts. Content edit, approval removal or archive invalidates active preparations; historical snapshots remain for audit. Preparation returns `externallySubmitted: false` and never enqueues a post. A cancel is permitted for workspace writers while still prepared. A tenant outsider cannot access the record.

No social OAuth connector, token storage/rotation, platform variant, automatic scheduler, publication worker, provider attempt or provider post ID is implemented. No UI should label a planned item or preparation as scheduled or published. No preparation is a policy clearance or consent to post.

The next phase must use official APIs and authorized accounts. Persist immutable approved revisions, publication attempts, idempotency keys, provider IDs and unknown-outcome states. A timeout must not trigger a blind duplicate post. Apply platform policy/metadata validation immediately before send; respect revoked authorization and manual overrides.
